## 1. Цель и полномочия

Цель: достоверный, удобный и технически устойчивый сайт, который приводит квалифицированные заявки на прибыльные перевозки. Главный бизнес-показатель — маржинальный доход от привлечённых сайтом перевозок с учётом расходов на привлечение.

Роман утверждает бизнес-факты, коммерческие условия и бюджет. ChatGPT ведёт план, формирует задания и разбирает отчёты. Cursor выполняет задачи в репозитории: создаёт issues, ветки, Pull Requests, исправляет ошибки, контролирует проверки и делает merge в пределах настоящего плана.

Создание issues/PR, исправления и merge после успешной приёмки разрешены пользователем заранее. Не просить подтверждение каждого такого шага. Существующие ограничения доступа, обязательные ревью и правила GitHub сохраняются. Если merge автоматически публикует сайт, учитывать это как выпуск: до merge проверить предварительную версию, после — результат публикации. Не создавать новый платный сервис и не запускать рекламные расходы без отдельного решения владельца.

Этот документ — проектное задание, а не доказательство выполненных изменений. В репозитории подготовлены PR #244–#249; по последним отчётам они не влиты. Наблюдения прежнего аудита перед изменениями перепроверять на актуальной версии кода.

## 2. Постоянная память проекта

PS-00 должен встроить этот план в существующую документацию, не перезаписывая полезные правила. Рекомендуемая структура, адаптируемая к репозиторию:

- `docs/project/PLAN.md`: задачи, зависимости, критерии приёмки.
- `docs/project/FACTS.md`: подтверждённые реквизиты и сведения, открытые вопросы.
- `docs/project/STATE.md`: текущая задача, issue/PR, последний проверенный коммит, блокировки, следующая задача.
- `docs/project/CI-CONTRACT.md`: точные идентификаторы проверок, правила merge, ветка, команды локальных проверок, деплой и откат.
- `docs/project/DECISIONS.md`: принятые решения и их основания.
- `.cursor/rules/pacificstar-workflow.mdc`: короткое правило `alwaysApply: true`, которое направляет Cursor читать документы и соблюдать цикл выполнения. Это правило проекта, не новый SKILL.md.

Статусы: BACKLOG → READY → IN_PROGRESS → IN_REVIEW → READY_FOR_CI → MERGED → VERIFIED. READY_FOR_CI означает локальную готовность, но не успешный удалённый CI и не публикацию. BLOCKED означает известную внешнюю причину остановки. VERIFIED разрешён только после проверки фактического результата, включая публикацию, если она входит в существующий процесс. MERGED не означает, что опубликованная версия уже работает.

До merge в STATE фиксировать готовность PR к приёмке. Фактический merge SHA, ссылки на проверки и послерелизный результат записывать в issue/PR. В следующем рабочем PR синхронизировать STATE. Не делать прямые коммиты в основную ветку ради обновления статуса и не создавать бесконечные PR ради записи SHA предыдущего PR. При восстановлении GitHub — источник истины о merge и проверках.

## 3. Регламент одной задачи

1. Прочитать правила репозитория, STATE, карточку задачи и зависимости. Проверить remote, ветку и незакоммиченные пользовательские изменения. Не трогать чужую работу; при необходимости использовать отдельный worktree.
2. Найти issue по стабильному идентификатору PS-XX. Создать при отсутствии. Не создавать дубликаты после перезапуска. В issue: проблема, объём, исключения, зависимости, критерии готовности, план проверки.
3. Создать рабочую ветку от актуальной целевой ветки. Одна задача — один небольшой PR; большой этап можно разделить на дочерние issues/PR с отдельной приёмкой.
4. Реализовать решение в существующем стеке. Не переписывать сайт на новый фреймворк ради удобства агента.
5. Проверить затронутую функциональность локально. Для расчётов, заявок и аналитики нужны содержательные проверки. Для простой замены реквизитов достаточно проверки источников и отображения; не городить тесты ради количества.
6. Для визуальных изменений проверить desktop 1440 px и mobile 390 px; дополнительно границы 360, 430 и 768 px. Сохранить скриншоты/артефакты без личных данных. Тестировать клавиатуру, формы и отсутствие перекрытий.
7. Создать или обновить PR со ссылкой на issue. Описать что изменилось, зачем, как проверено, ограничения и способ отката. Не ослаблять критерии issue после неудачной проверки.
8. Получить текущий HEAD SHA PR и результаты именно за эту ревизию. Дождаться всех трёх проверок из CI-CONTRACT, а также дополнительных обязательных правил GitHub.
9. Если проверка неуспешна: прочитать лог конкретного сбоя, исправить причину в коде/конфигурации этой задачи, обновить тот же PR и журнал issue, повторить локальную проверку и CI. Новый коммит обнуляет прежнюю готовность к merge.
10. Если всё успешно: убедиться, что HEAD не изменился, нет конфликтов и невыполненных обязательных ревью; сделать merge разрешённым в репозитории способом. Если действует merge queue — пользоваться ею и дождаться фактического merge.
11. Проверить статус PR на GitHub, получить merge SHA, дождаться существующего деплоя и выполнить smoke-проверку. При проблеме не переходить дальше; исправлять выпуск, при необходимости подготовить revert через тот же защищённый процесс. Не менять DNS, права и секреты для обхода ошибки.
12. Закрыть issue после выполнения критериев или переоткрыть автоматически закрытый issue, если результат не прошёл проверку. Записать отчёт и перейти к следующей READY-задаче с выполненными зависимостями без запроса нового промпта.

### Три проверки: строгий контракт

Утверждены GitGuardian Security Checks, PHP lint и HTML validation. Их внедрение — PR #247. По отчёту Actions заблокированы биллингом, GitGuardian проходит. Не повторять поиск исторической «тройки». Дополнительные требования защиты ветки сохраняются; недоступность настроек не доказывает отсутствие защиты.

Недостаточно увидеть любые три зелёные строки. Все ожидаемые проверки должны присутствовать и завершиться успешно для актуальной ревизии. Отсутствующая, ожидающая, отменённая, нейтральная или пропущенная проверка не считается выполнением договорённости о трёх успешных проверках. Если документационные изменения не запускают workflow из-за path filter, не подменять проверку фиктивным успехом; выяснить корректный способ запуска или обозначить блокировку.

Запрещены `--admin`, обход merge queue, отключение защиты веток, удаление/переименование падающих проверок ради merge, добавление continue-on-error ради зелёного статуса, фиктивные проверки, self-approval вместо обязательного независимого ревью, прямой push в основную ветку, force-push в основную ветку. Изменение CI допустимо как обоснованное исправление с сохранением покрытия и правил приёмки, а не как обход.

Использовать GitHub CLI или уже доступную интеграцию Cursor с GitHub. CLI позволяет смотреть проверки (`gh pr checks`) и привязать merge к ожидаемому HEAD (`gh pr merge --match-head-commit`). Одной команды `gh pr checks --required` недостаточно, если три пользовательские проверки не помечены в GitHub обязательными. Не включать auto-merge заранее, если защита ветки не гарантирует весь контракт; сначала самостоятельно подтвердить его выполнение. Все команды адаптировать к реальному owner/repo и PR; не исполнять плейсхолдеры.

### Повторения, блокировки и стоимость

Продолжать исправления, пока есть новая проверяемая причина и прогресс. Не повторять один и тот же push, тест или перезапуск без изменения гипотезы. Инфраструктурный сбой допускает обоснованный повтор, но не бесконечное ожидание. При повторении идентичной ошибки без прогресса сохранить диагностику и BLOCKED: причина, что пробовали, что требуется. Не увеличивать платные лимиты автоматически. Не подменять успех словами «скорее всего работает».

Если сессия/лимит Cursor закончились, сохранить продолжение. Промпт сам по себе не гарантирует постоянную фоновую работу. Возобновление должно продолжать существующий PR, а не начинать задачу заново.

Внешняя блокировка бизнес-данных может остановить часть задачи; можно перейти к следующей независимой READY-задаче, явно сохранив незавершённость. При поломанном выпуске сначала восстановить его. Блокировка CI запрещает merge, но не независимую разработку и локальные проверки; готовить зависимые PR с явными базами.

## 3А. Canva — обязательный этап работы над дизайном

Указание Романа: «при работе с дизайном применяй Canva».

- ChatGPT готовит дизайн-бриф и макеты в Canva: первый экран, главная, шаблоны услуг, карточки техники/кейсов, формы, desktop и mobile. Canva — источник согласованного визуального решения; Cursor реализует его в коде.
- До выполнения PS-07, визуальных частей PS-08, PS-09 и PS-10 создать или выбрать соответствующий макет Canva. Для каждого сохранить настоящий design URL/ID, дату/версию, экспорт экранов, размеры, шрифты, цвета, интервалы, состояния компонентов и правила адаптации. Не придумывать ссылок и не считать текстовый отчёт с идеями готовым макетом.
- Четыре ранее сгенерированных кандидата Canva были концептуальными документами, их содержимое не прошло визуальную приёмку, пользователь вариант не выбрал. Это не утверждённые макеты сайта и не основание для произвольной реализации.
- Для нового главного визуального направления показать Роману конкретный макет для выбора/согласования; затем использовать выбранную систему на остальных страницах. Это содержательное решение о дизайне, не повторное разрешение на технические merge.
- Cursor не обязан иметь встроенный доступ к Canva: использовать реально подключённую интеграцию, а при её отсутствии экспорт PNG/PDF и отдельную спецификацию. Недоступность Canva нельзя обходить словами «сделано в Canva» или подменять выдуманным макетом. Подготовку Canva ведём здесь; Cursor отмечает зависимость DESIGN_READY и может продолжать независимые технические задачи.
- Экспортированный макет не переносить на сайт как одну картинку: реализовать семантическую HTML-разметку, доступные формы, адаптивную сетку и текст, доступный поисковикам. Изображения и логотипы использовать с разрешёнными правами; не выдавать сгенерированную иллюстрацию за фотографию собственного парка.
- Технические меры доступности и скорости в PS-06 можно внедрять без ожидания нового макета; это не разрешение на самостоятельный редизайн в обход Canva.
- В PR с дизайном приложить ссылку/версию Canva, исходный экспорт и скриншоты реализации в тех же размерах; описать допустимые отличия из-за адаптивности. Три проверки GitHub обязательны, но не заменяют визуальную сверку.
- В будущих промптах Cursor всегда включать DESIGN_REFERENCE (реальная ссылка/экспорт), размеры desktop/mobile и критерии сравнения. Пока этих данных нет, дизайн-задача имеет статус BLOCKED_BY_DESIGN, а не VERIFIED.

## 5. Последовательность работ

Все номера PS-XX — стабильные идентификаторы плана, не номера GitHub issues. После PS-00 Cursor создаёт issues без дублей и связывает зависимости. Этапы с внешними данными можно выполнять частично, но нельзя отмечать полностью завершёнными до получения доказательств. Рекламные расходы и изменения во внешних кабинетах не входят в автоматический цикл работы с кодом.

### PS-00. Подготовить управляемый рабочий процесс — READY

Зависимости: открыт правильный репозиторий сайта и есть доступ к GitHub.
Работа: установить remote/default branch, стек и команды, прочитать действующие инструкции, проверить незавершённые PR/issues, права issues/PR/merge, три проверки, правила ревью, preview/deploy/rollback. Сохранить исходный SHA. Создать проектную документацию и постоянное правило Cursor. Зафиксировать факт автопубликации после merge или её отсутствие. Сделать первый PR только с документами/правилом.
Приёмка: известны три проверки и условия допуска; первый PR прошёл их без обхода и влит; записаны команды продолжения. Если доступ недостаточен, документировать точную блокировку. Не спрашивать заново общую авторизацию на merge.

Ясно разделить первичный ответ и расчёт проекта.
Приёмка: нет конфликтующих обещаний; сведения экспедитора не выдаются за регистрацию оператора; неизвестные факты не опубликованы как проверенные. Подтверждение удалённых показателей и возвращение доказанного содержания — отдельное продолжение, не блокирующее технические задачи.

### PS-03. Сделать приём обращений надёжным

Зависимость: PS-00; учитывать контакты PS-01. Приоритет P0.
Работа: проверить реальные обработчики и способ доставки обращения; валидация на сервере, обработка ошибок и повторного нажатия, отсутствие потери введённого текста, защита от очевидного спама; понятный успешный ответ с идентификатором обращения по возможности. Уведомление об успехе только после подтверждённого приёма, не просто клика. Проверить ограничения вложений, если они уже есть; новую загрузку файлов внедрять с серверной проверкой размера/типа и безопасным хранением.

Развести пересекающиеся страницы авто/труднодоступных районов; не удалять URL без плана перенаправления.
Приёмка: из главной можно найти нужную услугу и связаться; нет сломанных внутренних ссылок; ключевые URL сохранены или имеют согласованные 301; карту можно заменить текстовым выбором без потери функции.

### PS-10. Создать доказательную базу: парк, кейсы, документы

Приёмка: шаблоны работают; опубликованные карточки имеют источник фактов. Полнота базы требует материалов владельца и отражается отдельными BLOCKED-подзадачами. Не выдавать готовый пустой шаблон за завершённую страницу с доказательствами.

### PS-12. Связать сайт с CRM и отчётностью продаж

Приёмка: тестовое обращение прослеживается до CRM с корректным источником; сбой доставки не теряет данные. До доступа можно подготовить интерфейс и документацию, но интеграцию не считать действующей. Не покупать CRM и не менять рабочие воронки без соответствующих полномочий.

### PS-13. Вернуть корректный тарифный расчёт при наличии данных

Приёмка: согласованный набор реальных эталонных примеров пройден; отклонение укладывается в утверждённые логистом границы; просроченные ставки не выдаются как действующие. Пока данных нет, PS-05 остаётся корректным рабочим решением.

Зависимости: все внедрённые этапы. Приоритет P1 для релиза, далее регулярно.

Зафиксировать владельца обновления реквизитов, тарифов, сезонности и кейсов.
Приёмка: три проверки успешны для выпуска, smoke пройден, ограничения перечислены; внешние проверки не отмечены как выполненные без доказательств. Зафиксирован исходный уровень маркетинговых показателей для дальнейшего сравнения.

## 9. Может ли Cursor автоматически обращаться к этому чату?

В этой сессии нет настроенного входящего webhook, который позволял бы Cursor разбудить этот чат и получить следующий промпт. Не обещаем такую связь. Самый экономный вариант — выдать план/очередь заранее и позволить Cursor продолжать её в пределах действующей сессии. Роман приносит сюда отчёт для пересмотра плана при необходимости.

Отдельный сервис «событие GitHub → проверка результата → запрос к модели через API → следующее задание» технически можно спроектировать, но это другая интеграция, с отдельным состоянием, авторизацией и расходами API. Она не обращается автоматически к текущей переписке. Для неё потребуются ограничения бюджета, проверка подписи webhook, защита от повторов, запрет реакции на собственные комментарии и обработка недоверенного текста issue. Сейчас её не внедрять: очередь задач в репозитории решает основную задачу дешевле.
